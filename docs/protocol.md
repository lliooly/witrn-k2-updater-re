# WITRN K2 固件格式与 HID 协议

本文记录对 WITRN UP V30 Windows 主机程序的静态分析结果，以及 Python 实现采用的协议模型。实现范围和分析输入见[反向工程报告](../reverse/REPORT.md)。协议细节可能因设备或 Bootloader 版本变化；静态分析与单台设备实测都不能证明对所有 K2 的兼容性。

## 证据与边界

分析过程恢复了受保护程序集中的方法体和代理调用，并检查了升级 worker 的控制流。Python 实现按此重建主机行为。一次单台 K2 的 DFU 实测覆盖握手、信息读取、3.4 → 5.8 升级、应用正文读回、提交标记和退出确认。设备日志和备份不随仓库发布。

没有证据表明固件中的 XOR 与加法和是数字签名或来源认证；它们只用于格式/错误检查。**固件通过本地校验不代表固件可信。**请只使用你信任来源的固件。

## 固件容器

文件先经过 256 项逐字节替换表解码，再解析 48 字节头部和应用正文。表由 `k2up/data/firmware_decode.bin` 提供。

| 解码偏移 | 长度 | 字段 | 说明 |
| --- | ---: | --- | --- |
| `0x00` | 7 | 魔数 | ASCII `gzutapp` |
| `0x07` | 4 | 日期 | 年为 LE16，月、日为 U8 |
| `0x0B` | 9 | 保留 | 已观察样本为 `FF` 填充 |
| `0x14` | 16 | 型号 GUID | GUID 的小端字段布局；K2 为 `5a3f8522-366b-46cc-aacc-dbfbe2fee02a` |
| `0x24` | 4 | 正文长度 | LE32 |
| `0x28` | 4 | 正文 XOR | LE32 |
| `0x2C` | 4 | 正文加法和 | LE32，模 2³² |
| `0x30` | 可变 | 应用正文 | 写入地址从 `0x08003800` 开始 |

解析器检查魔数、日期、GUID、长度、XOR、加法和、未提交标记、栈指针和复位向量范围。正文偏移 `0x800` 的字节按高低半字节显示应用版本；偏移 `0xC00` 是四字节提交标记。升级写入前要求该标记为 `FF FF FF FF`，读回全正文一致后写入 `FE FF FF FF`。

扇区配置为 447 个连续的 2 KiB 区间，覆盖至 `0x080E3000`（末地址不含）。升级器按整个容器长度计算擦除范围，因此 48 字节头部也计入擦除长度。

## 64 字节帧

主协议帧长 64 字节。多字节值在负载中为小端序。

| 偏移 | 长度 | 含义 |
| --- | ---: | --- |
| `0x00` | 2 | 固定字节 `FF 55` |
| `0x02` | 1 | `tick / 1000`，截断为 U8 |
| `0x03` | 1 | `tick % 1000`，截断为 U8 |
| `0x04` | 1 | 回包标志和 `tick / 30`：请求响应时置高位，不等待响应时清高位 |
| `0x05` | 1 | `tick / 100`，截断为 U8 |
| `0x06` | 1 | `tick % 100` |
| `0x07` | 1 | `tick / 80`，截断为 U8 |
| `0x08` | 1 | 命令 |
| `0x09` | 1 | 负载长度，最多 52 |
| `0x0A` | 52 | 负载和零填充 |
| `0x3E` | 1 | 内层校验：`sum(frame[8:62]) & 0xFF` |
| `0x3F` | 1 | 外层校验：`sum(frame[0:62]) & 0xFF`，不含内层校验字节 |

静态分析表明主程序的时间值来自 `Environment.TickCount`；Python 使用单调毫秒时钟并按 U32 回绕。Windows HID 包装层和 HIDAPI 的报告 ID 处理方式不同；Python 输出使用零前缀加 64 字节帧，输入接受 64 字节帧或零前缀的 65 字节报告。此适配已在一台 K2 上验证，其他平台仍需实测。

## 命令

所有请求负载中的地址和长度均为小端序。控制命令的 ACK 使用命令 `2` 表示成功、`1` 表示设备错误。读取请求直接返回同命令号的数据包。默认响应超时为 1000 ms。

| 命令 | 请求负载 | 行为 |
| ---: | --- | --- |
| `3` | 空 | 握手，等待 ACK |
| `5` | 空 | 打开写入批次，等待 ACK |
| `4` | 空 | 关闭批次，等待 ACK |
| `8` | 地址 U32 | 擦除一个配置扇区；不等待单扇区 ACK |
| `9` | 地址 U32 + 长度 U8 + 数据 | 写入最多 40 字节；分包不等待单包 ACK |
| `10` | 地址 U32 + 长度 U8 | 短读取，数据以命令 `10` 回包 |
| `11` | 地址 U32 + 长度 U16 | 批量读取，以最多 40 字节分包，数据以命令 `11` 回包 |
| `21` | 级别 U16 + 序号 U16 + 长度 U8 + ASCII 文本 | 设备日志包 |
| `22` | 空 | 重置日志状态，等待 ACK |
| `23` | 空 | 结束升级会话，等待 ACK |

协议没有发现可用于关联请求和 ACK 的序列号。实现会在新事务前清空已到达的日志包并拒绝未消费响应，不自动重试，也不并行运行升级会话；仍无法排除恰好延迟到下一事务的同类 ACK。

## K2 参数与识别

| 参数 | 当前实现值 |
| --- | --- |
| VID:PID | `0716:5060` |
| 型号 GUID | `5a3f8522-366b-46cc-aacc-dbfbe2fee02a` |
| 应用起点 | `0x08003800` |
| 设备信息区 | `0x08003000`，读取 1024 字节 |
| 名称区 | `0x08001400`，读取 256 字节，含三个 NUL 结尾 UTF-8 字符串 |
| 扇区范围 | 447 × 2048 字节，至 `0x080E3000`（不含） |
| 提交地址 | `0x08004400` |
| 提交值 | `FE FF FF FF` |

VID/PID 和固件 GUID 本身不足以确认设备型号。实机写入前还会解析设备返回的三个名称字符串；当前仅接受实现中列出的 K2 名称。不要为了绕过不匹配而移除检查。Bootloader 名称区或回包格式变化时，应先用只读探测与协议证据更新实现。

## 升级顺序与停止行为

1. 在打开 USB 前完整校验固件容器及向量。
2. 握手，读取设备信息和名称，确认 K2；清理日志状态。
3. 打开批次，擦除覆盖固件容器长度的扇区，关闭批次。
4. 打开批次，将应用正文按 1024 字节主机块和最多 40 字节 HID 写包写入，关闭批次。
5. 按最多 1024 字节读取整份应用正文并逐字节比较。
6. 只有正文完全一致才写 `FE FF FF FF`；短读回核对后关闭批次。
7. 发送命令 `23` 并等待 ACK。

任何阶段失败都会停止，不发送自动收尾或重试命令。发生在擦除之后的失败可能留下不完整应用。`backup` 是只读双遍读取并比较后才生成本地恢复容器；这并不证明该恢复容器已能在真实设备上回刷，也不替代其他备份方式。

## 验证范围

仓库测试使用合成样本和内存模拟传输，不访问 USB。模拟器用于检查主机端状态顺序、地址范围、读回比较与失败停止行为，不是 Bootloader 仿真器。硬件证据只覆盖一台 K2 的一次 3.4 → 5.8 过程；没有验证其他硬件修订、Bootloader 版本或恢复刷写。实机捕获、设备备份与厂商二进制不会提交到本仓库。

## DFU 读取性能实测

2026-10-10 使用同一台 K2（应用版本 5.8）执行只读对比。先读取并核对 14336 字节 Bootloader 与信息区，其 SHA-256 为 `406e15789802ff58f534b0d9550b041580104168d6c543d6fb02b198449424e7`。每组读取同一段应用数据，轮换测试顺序并重复三轮，所有结果均与基准逐字节一致。测试只发送命令 `3`、`10`、`11`。

| 同一段数据 | 请求方式 | 三轮耗时中位数 |
| --- | --- | ---: |
| 32768 字节 | 命令 11，每次 1024 字节 | 1.558 秒 |
| 32768 字节 | 命令 10，每次 40 字节 | 2.324 秒 |
| 32768 字节 | 命令 10，每次 48 字节 | 1.936 秒 |
| 32768 字节 | 命令 10，每次 52 字节 | 1.789 秒 |
| 65536 字节 | 命令 11，每次 1024 字节 | 3.116 秒 |
| 65536 字节 | 命令 11，每次 1000 字节 | 3.071 秒 |
| 65536 字节 | 命令 11，每次 4000 字节 | 3.024 秒 |
| 65536 字节 | 命令 11，每次 16000 字节 | 3.011 秒 |

这份 Bootloader 的命令 10 将请求长度的数据放进单个回包，52 字节恰好占满帧负载；它没有批量读取的两处发送等待，但每次请求的往返开销使其实际更慢。命令 11 使用 U16 长度和固定 40 字节数据分包，在发送前后等待 USB 端点就绪；实测相邻读取回包约间隔 2 ms。增加主机请求长度无法增加设备的单帧有效数据，也不能直接移除设备端的等待。

在已分析的命令分派表中，`12`–`20` 没有读取校验和的处理，未找到可供主机调用的整段 CRC 或摘要命令。这是对这一份 Bootloader 的结论，不代表其他版本。

16000 字节请求比现有请求的样本耗时低约 3.4%。按一次升级日志中的两次备份读取（各约 44.2 秒）和升级后读回（约 34.1 秒）推算，合计约省 4 秒；这是推算，未进行完整升级测速。更大请求只在研究工具中使用，正式备份和升级协议保持原样。第二遍备份本来就按收到的块立即比较；把比较与传输重叠无法省去第二遍 USB 数据。若要明显缩短两次读取，仍需经过验证的设备端校验接口或更快的设备发送实现。

测速工具与使用方法见[研究目录](../reverse/README.md#dfu-只读测速)。原始捕获和 JSON 结果保存在本地忽略目录，不包含在仓库提交中。
